# Decisions

Stage 1 listed these as proposals. After the Stage 1 review the owner asked for everything judged wrong to be fixed, with one ground rule: no data may be created, assumed, simulated or filled in; everything uses real data. The decisions below record what was applied and any change from the Stage 1 proposal.

| D37 | Commit authorship by per-commit flags only | applied | The repository has no configured Git identity; a commit without one would carry the laptop default address. `git -c user.name=... -c user.email=...` sets the author for that command and changes no configuration | No Git configuration was modified |
| D38 | `test_E28b_readme_describes_the_implemented_convention` was adapted, not weakened | applied | The README now states "not buy-and-hold" on purpose; the test now requires every mention of buy-and-hold to be negated and requires the daily-rebalancing sentence, and still forbids the ambiguous phrase "held fixed over the test period" | A guard on what the README may claim, strengthened in one respect and changed in another; the reason is recorded here and in `VALIDATION_REPORT.md` section 13 |

| D42 | An infinite value anywhere in a rolling history raises `ValueError`; NaN keeps its policy (affected windows have no forecast) | applied (was: recorded, not changed) | Infinity is neither a missing return nor a valid one. Converting it to NaN would hide a data error, and leaving it produced an ordinary-looking number (historical) or NaN (normal). The data layer already guarantees finite returns, so valid data never reaches the check | The owner asked for rejection; `backtest.rolling_forecasts` checks before any calculation, including for histories too short to forecast |
| D43 | Invalid inputs raise `ValueError` (or `RuntimeError` for a failed optimiser) with a message that names the problem; they are never coerced, dropped or filled | applied | The module audit found price tables with duplicate or unsorted timestamps and non-positive prices, windows such as 0, 1, 2.5 or `True`, fractional or boolean Kupiec counts, non-finite or misaligned score inputs, unvalidated configuration and NaN optimiser weights all accepted silently (`ALL_MODULES_VALIDATION.md` section 5, D-1 to D-6) | Closes the "other arguments of the backtest functions are not validated" item of `VALIDATION_REPORT.md` section 25; valid input behaves exactly as before |
| D44 | An undefined statistic stays NaN in code, null in JSON and the word "undefined" on screen (and in the README tables); beta against a constant benchmark is undefined | applied | A constant benchmark gave a beta of 19.2; the dashboard printed "n/a" for some undefined values and crashed on a null rank IC or Sharpe | The wording "n/a" is replaced by "undefined" in the dashboard |
| D45 | The random forest is fitted in parallel and used for prediction single-threaded | applied | Parallel prediction sums the per-tree outputs in thread-completion order, so forecasts differed in their last bit between identical calls (300 distinct outputs in 300 calls) and a pipeline rerun could differ in the last digit of a statistic | Speed of fitting is unchanged; the fitted trees are identical; every regenerated result file still equals the checked-in one |
| D46 | The dashboard loads every results file, including the membership summary, inside one guarded block and checks required columns and keys | applied | A missing membership summary raised a raw `FileNotFoundError` and a wrongly shaped file raised a `KeyError` inside a tab; `scripts/check_sp500_membership.py` raised raw pandas errors on damaged cached tables | Both now stop with a message naming the file and the command that recreates it; no partial output is written |
| D47 | Coverage is measured with `pytest-cov` and `coverage` (added to `requirements.txt`, pinned); the scripts that tests run as subprocesses are measured only when `COVERAGE_PROCESS_START` is set | applied | Package-only coverage had hidden that `data.py` was 39.9% covered; scripts and the dashboard were not measured at all | Not a requirement for running the tests; `.coveragerc` maps the temporary trees back to the repository paths |
| D48 | A portfolio with zero volatility has an undefined Sharpe ratio: reported as NaN in performance figures and the metrics table, and refused in the optimiser (`ZeroVolatilityError`, a `ValueError`) so that `fit` reports the preset as not constructed with the reason | applied | The objective returned 0.0 at zero volatility, so the optimiser could stop at the equal-weight starting point and report a successful allocation for constant returns or for holdings that cancel exactly, for any sign of the excess return; rounding-level volatility (about 1e-19) gave a Sharpe ratio of about 1e18 | Same refusal design as non-convergence and infeasible bounds. "Zero" means annualised volatility at or below `MIN_VOLATILITY = 1e-12` (a numerical floor, not a statistical threshold; real series are about 1e-1). No screen, bound, date, seed or reported number changes |
| D49 | The snapshot is updated incrementally: only days after the last stored date are downloaded, with a one-week overlap checked against the stored prices; a ticker whose overlap no longer matches (tolerance 1e-6 relative) is downloaded in full again and replaced; nothing is rescaled | applied | `fetch_data.py` downloaded the whole history every time. Yahoo's adjusted prices change retroactively after a dividend or split, so appending new days to an old adjusted history would put a jump at the join; replacing only the tickers that changed keeps the stored history equal to what a complete download gives | `fetch_data.py` is unchanged and remains the way to create the first snapshot; `update_data.py --full` repeats a complete download. The default end date is today (exclusive) so an unfinished trading day is never stored |
| D50 | The interactive dashboard is published on GitHub Pages by running the unchanged `dashboard/app.py` in the visitor's browser with stlite (Streamlit on Pyodide), version-pinned, with a byte copy of the code, `results/` and the price snapshot built into the published pages | applied | GitHub Pages serves static files only and cannot run a Python server; a hosted Streamlit server would need a separate account and a start-up download of the price data | Trade-offs: the first load takes about a minute and downloads packages from the jsDelivr CDN (plotly from PyPI); the Yahoo Finance price snapshot becomes publicly downloadable from the site, which Yahoo's terms may not allow, so the owner may prefer to remove it; the static report stays as the fast page |
| D51 | The pages are built and published by a daily GitHub Actions workflow, on a `pages` branch that is replaced by a single new commit each time, not kept on main | applied | The published price file is about 6.5 MB and changes with every trading day, so committing it to main daily would grow the repository by roughly 1.6 GB a year; the replaced branch keeps one copy. The same branch is the only place the price snapshot is stored for the workflow | Pages source changed from main `/docs` to the `pages` branch `/`; `docs/` is generated locally and git-ignored. Force-pushing the `pages` branch is intended: it holds nothing but generated files |
| D52 | A re-downloaded history replaces a stored one only if it has a price on at least 90% of the stored dates; known failed tickers are not retried by a daily run | applied | A real update on 2026-10-26 showed Yahoo returning a single day of another company for the symbol PARA, which would have replaced 1,431 stored days; retrying 21 delisted tickers cost about five minutes of waiting | `--retry-failed` retries them; the history rule has no override |
